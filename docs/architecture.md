# Architecture

- **Static, no backend.** The app ships as static files plus a service worker (PWA, works offline). Anything that would need a server is out of scope unless a decision record says otherwise.
- **Lyrics search** calls the LRCLIB API (`https://lrclib.net/api/search`) straight from the browser. Paste is the fallback for every case search can't cover (no result, instrumental, wrong lyrics).
- **Library** lives in browser storage on each device; there are no accounts and no sync. Export/import of a library file is the backup and the only cross-device path.
- **App-wide settings** (paper size and orientation; theme later), and the time of the last Backup that paces the nudge to export, live in localStorage behind `src/app/settings.ts`, read synchronously while rendering. They are small and easy to set again, so they stay out of the Library and its export file.
- **One fit engine** lays out a Song for both a Screen and a Sheet. It never splits a Stanza; its fallback order is more columns → smaller font down to a minimum → spill to another Screen/Sheet. A column is readable, and so allowed, when the widest line of every Stanza fits it unwrapped. The one exception to never splitting: when Spilling, a Stanza taller than a whole column at the minimum font breaks between lines, only where a column is full. The engine owns the gaps between Stanzas and columns (in em); the views apply the same values. Screen and Sheet differ only in their inputs (dimensions, minimum font size).
- **Per-song display overrides** (size, columns) apply to Screens only; Sheets always auto-fit, on the paper chosen in Settings (landscape just swaps width and height). An Override fixes the font size, the column count or both, and the Fit engine works out the rest the usual way; a fixed column count is filled evenly rather than first-column-first, so asking for more columns shows them. A fixed column count is used even where it is not readable: lines wrap rather than the Override being ignored.
